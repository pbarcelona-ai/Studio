# video_processor

## Code Review Guidelines

These apply only to the following source files in this project:

| Language      | Extensions                                   |
|---------------|----------------------------------------------|
| SystemVerilog | `.sv`, `.svh`                                |
| C             | `.c`, `.h`                                   |
| C++           | `.cpp`, `.cc`, `.cxx`, `.hpp`, `.hh`, `.hxx` |
| Python        | `.py`                                        |
| HTML          | `.html`                                       |

Whenever one of these files is created or modified, review the new version against the
checklist below (a PostToolUse hook in `.claude/settings.json` reminds you after each edit).
Other file types are not reviewed, except that a change to a `*_prompt.md` requirements file
triggers a review of its module (see Requirements Checks). Source: `code_reviewer_prompt.txt`.

### Lower-level modules
Whenever a new or changed file is reviewed, also review every lower-level module beneath it,
recursively down to the leaves:

- **SystemVerilog:** every module, interface and package the file instantiates or imports.
  Resolve each to its source through `scripts/build.f` (RTL) or `tb/scripts/build.f`
  (testbench); this includes IP under `../../ip/`.
- **C / C++:** every project header in `#include "..."`, and the `.c` / `.cpp` that implements it.
- **Python:** every project-local module the file imports (`sw/`, `tb/scripts/`,
  `python-prototype/` and similar). Skip the standard library and third-party packages.

Rules:
- Review each lower-level file once per review pass, even if several files use it.
- Write a separate result file for each one: `code_reviews/<file_name.ext>_review.txt`, in the
  same format as the top-level review.
- Also review how the parent uses each lower-level module: port and parameter connections,
  widths, clock and reset domains, protocol assumptions (SystemVerilog); call signatures and
  return-value and error handling (C / C++ / Python). Report these in the parent's review.
- A lower-level file that has not changed since its existing review file was written (source
  older than the review file) may reuse that review: list it in the parent's review as "reviewed
  <date>, unchanged". Do not reuse a review if the source is newer than its review file.
- At the top of the parent's review, list the hierarchy that was reviewed (file -> lower-level
  files).

### Requirements Checks
Every reviewed module is also checked against its requirements file, `<module name>_prompt.md`:

- **Where:** `<ip_dir>/docs/<ip_name>_prompt.md`, where `<ip_dir>` is the IP directory that holds
  the source in `src/` (e.g. `../../ip/video/isp_gamma/src/isp_gamma.sv` ->
  `../../ip/video/isp_gamma/docs/isp_gamma_prompt.md`; `src/video_processor.sv` ->
  `docs/video_processor_prompt.md`). Helper files in the same `src/` (e.g. `*_regs.sv`, `*_top.sv`,
  sub-blocks) are checked against the same file for the parts of it they implement.
  Python programs: `<owner>/docs/python/<name>_prompt.md`, where `<owner>` is the design
  (e.g. `sw/video_proc.py` -> `docs/python/video_proc_prompt.md`), the IP directory, or `ip/` for
  the library tools (generated by `ip/scripts/make_py_prompts.py`). Firmware (`sw/`) is also checked
  against the register maps it drives (`<ip>/src/include/<ip>_regs.json`) and must compile with
  `pyc.py`.
- **Industry reference:** section 6a of each prompt (from `docs/<name>_reference.md`, or
  `docs/python/<name>_reference.md`) compares the requirements with published engineering references;
  every open `TODO(REF-...)` there is a finding of the review until it is resolved or documented.
- **What:** go through the requirements one by one and check the design implements each: ports
  and interfaces, parameters and their ranges, register map (offsets, access types, reset
  values), functions and modes, data formats, clocking and reset behaviour, latency and
  throughput, error handling. Report:
  - requirements that are missing or implemented differently (with the requirement quoted and
    the file / line that differs),
  - behaviour in the design that the requirements do not describe,
  - places where the header comment of the source and the requirements file disagree.
- **Report:** in a `Requirements` section of the file's review, ranked with the other findings
  (a missing or wrong required function is at least MEDIUM). If every requirement is met, say
  "Requirements: all met (<prompt file>)".
- **No requirements file:** state "Requirements: no <module name>_prompt.md found" in the review.
- **Requirements file changed:** when a `*_prompt.md` is created or modified, review the module(s)
  in its IP's `src/` against it (with the lower-level rules above). The PostToolUse hook triggers
  this as for source edits.

### SystemVerilog-Specific Checks
Apply these to `.sv` / `.svh` files in place of the software-only items above:
- **Inferred latches**: `always_comb` blocks or combinational `case`/`if` without full
  assignment of every output on every path (missing `default`, missing `else`)
- **Blocking vs. non-blocking**: `<=` in `always_ff`, `=` in `always_comb`; no mixing within
  one block; no plain `always` where `always_ff`/`always_comb` is intended
- **Clock-domain crossings**: every signal crossing clock domains goes through a proper
  synchronizer (2-FF for single bits, gray code / async FIFO / handshake for buses);
  flag any unsynchronized crossing
- **Reset coverage**: every stateful register has a defined reset value (or a deliberate,
  documented reason not to); consistent sync vs. async reset style; reset deassertion
  synchronized to the destination clock
- **Width mismatches**: implicit truncation or zero-extension in assignments, comparisons,
  and port connections; signed/unsigned mixing; unsized literals in arithmetic
- **Use before declaration**: every signal, variable, parameter, typedef and function is
  declared before its first use in the file, including uses in continuous assignments, port
  connections, `always` blocks, functions and generate blocks, and in every `ifdef`
  configuration (a declaration inside one `ifdef` branch must cover all uses enabled by that
  branch). Implicit nets are not allowed: every port connection must name a declared signal
  (`default_nettype none` is recommended)
- **Synthesizability**: no `initial` blocks, delays, or simulation-only constructs in RTL
  (outside testbench / `ifdef` guards)
- **FSMs**: unreachable or stuck states, missing `default` recovery, encoding consistency
- **Testbench (tb/)**: race conditions between TB and DUT, missing timeouts, assertions
  and coverage that actually check the behavior under test

### HTML-Specific Checks
Apply these to `.html` files:
- **Semantic Structure**: Correct use of HTML5 semantic elements (`<header>`, `<nav>`, `<main>`, `<section>`, `<article>`, `<aside>`, `<footer>`); proper heading hierarchy (`h1`–`h6` without skipping levels); landmark roles where needed.
- **Accessibility (WCAG 2.1 AA)**:
  - All non-text content has text alternatives (`alt` on images, `aria-label`/`aria-labelledby` on icon buttons, captions/transcripts for media).
  - Sufficient color contrast (≥4.5:1 normal text, ≥3:1 large text/UI components).
  - Keyboard operability: all interactive elements reachable and operable via keyboard; visible focus styles; no keyboard traps.
  - Form labels: every `<input>`, `<select>`, `<textarea>` has an associated `<label>` (explicit `for`/`id` or implicit wrapping).
  - ARIA: only when native HTML cannot achieve the same; `role`/`aria-*` attributes valid and not conflicting with native semantics; live regions for dynamic updates.
  - Language declaration: `<html lang="...">`; `lang` on sections with different language.
- **Forms & Input Validation**: proper `type` attributes (`email`, `tel`, `url`, `number`, etc.); `autocomplete` values; `required`, `pattern`, `min`/`max`/`step` where appropriate; server-side validation never replaced by client-only checks.
- **Security**:
  - No inline event handlers (`onclick="..."`) – use `addEventListener` instead.
  - No `javascript:` URLs.
  - CSP-compatible: no inline scripts/styles unless `nonce` or hash used; external scripts have `integrity` and `crossorigin` attributes.
  - Forms use `POST` for state-changing actions; CSRF tokens where applicable.
  - `rel="noopener noreferrer"` on `target="_blank"` links.
- **Performance**:
  - Critical CSS inlined; non-critical CSS loaded asynchronously (`media="print" onload` or `preload`).
  - Scripts use `defer` (default) or `async` appropriately; no blocking scripts in `<head>` unless necessary.
  - Images: appropriate formats (WebP/AVIF with fallbacks), `srcset`/`sizes` for responsive images, `loading="lazy"` for below-fold, explicit `width`/`height` to prevent CLS.
  - Fonts: `font-display: swap`; preconnect/preload critical origins.
  - Minimize DOM depth and node count.
- **Responsive & Mobile**: viewport meta tag present (`width=device-width, initial-scale=1`); fluid layouts with CSS Grid/Flexbox; touch targets ≥48×48px; no horizontal scrolling.
- **SEO & Metadata**: unique descriptive `<title>`; meta description; Open Graph / Twitter Card tags; canonical URL; structured data (JSON-LD) where appropriate.
- **Code Quality**: valid HTML5 (validator.w3.org); consistent indentation (2 spaces); lowercase tags/attributes; double-quoted attribute values; no deprecated elements (`<font>`, `<center>`, `<frame>`, etc.) or attributes (`align`, `border` on tables, etc.); comments only where they clarify intent.
- **Progressive Enhancement**: core content/functionality works without JavaScript; enhancements layered on top.

Provide your review in a clear, actionable format with specific line references and code suggestions where applicable, such that it can be read in as a prompt for execution on the individual file being reviewed. Place the review in a folder code_reviews. Name each result file <file_name.ext>_review.txt within that folder, keeping the source file's extension (e.g. `video_processor.sv_review.txt`, `foo.c_review.txt`, `foo.h_review.txt`) so files that differ only by extension don't overwrite each other. If nothing is identified, create the result file with the contents "<file_name.ext> <cr> No Issues Found".

### Automated Review Output
In addition to the individual review files, all findings from the current review pass shall be aggregated and written to `results.txt` in the project root. The `results.txt` file must contain:
- A summary of all files reviewed
- All findings (errors, warnings, suggestions) with file paths and line numbers
- A final status: "PASS" if no blocking errors, "FAIL" if any blocking errors exist

### Auto-Fix Loop
After writing `results.txt`, the system shall automatically fix all identified errors (not warnings or suggestions) by editing the source files. The review shall then be re-run on the fixed files. This loop continues until `results.txt` shows "PASS" (no blocking errors). Only after `results.txt` shows "PASS" shall the response "updated try again" be given.
